## 本轮新增

### 1. 可以单独打包网页

```powershell
node scripts/build-journal-site.js
```

先检查正式论文库及文件校验值，通过后再创建一份新的网页版本。网页只包含8个文件：两个页面、两个脚本、两份样式、精简论文数据和静态托管标记。不会把整个仓库、密钥、原始来源页或翻译工作文件打进网站。

现在正式库尚未初始化，普通打包会明确停止。如果只是检查空界面打包，可明确运行：

```powershell
node scripts/build-journal-site.js --allow-empty
```

这只构建“尚无论文”的界面，不会创建正式论文库或虚构论文。即使加了该参数，损坏的库也不会被当作空库。

电脑上 npm 可用时，`npm run journals:build` 是等效快捷命令；本机实际验证使用上述 node 命令，不需要修改环境设置。

输出在 `data/site-builds/versions/<构建编号>/site/`；程序会给出完整目录。每次生成新版本，不覆盖或删除旧网页目录。文件全部回读校验通过后，最后才更新 `data/site-builds/current.json` 这个“指向最新版本的小入口”。

如果中途失败、文件被改坏、或混进不应发布的额外文件，新版本不会成为当前版本。上一次成功的网页仍保留。本地构建不等于上传或上线；这些输出目前被 Git 忽略。

### 2. 明确哪些论文文件可以提交

```powershell
node scripts/journal-git-files.js --check
```

这条命令只读检查，沿正式版本的历史关系校验文件，不扫描整个数据目录来打包。保留当前版本及完整正式历史，但排除翻译草稿、写入锁、未提交的尝试记录和孤立半成品。

只有显式使用 `--stage` 才会修改 Git 暂存区；即使如此也不执行提交或推送。若暂存区已有用户文件，先停止，不把这些文件混进论文提交。本轮没有在当前仓库运行 `--stage`、`commit` 或 `push`。

### 3. 准备了未启用的自动流程

模板位于 `deploy/github/`，不是正在运行的 `.github/workflows/`。

- 采集模板：先测试和校验，再双源采集、保存正式历史，随后构建网页，最后可选发布。
- 单独发布模板：只发布已有论文和译文，不采集、不翻译。
- 来源部分失败时，仍可保存合格论文和失败日志，但运行最后会如实报告失败。
- 持久化失败、完整历史损坏或构建失败时，不把后续半成品上线。
- 采集与发布分别有启用开关，默认没有设置；不需要翻译 API Key。

流程按 [GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages) 准备了任务依赖、最小权限和发布环境。完整技术说明及固定组件出处见 [模板说明](../deploy/github/README.md)。

## 保存范围仍需你确认

模板拟将完整正式论文库保存到**同一 GitHub 仓库的默认分支**，不是只放在会过期的临时缓存中。这是待启用的实现方案，本轮未改变任何远端仓库。

网页展示的数据是精简版，但仓库里的正式历史含原始来源记录。如果仓库公开，这些提交也会公开。正式启用前，需要确认仓库归属及可见性、公开内容范围、默认分支保护规则和这个保存方案。若需要改为私有数据仓库，要先调整流程，不能直接套用模板。

模板有尚未启用的北京时间08:17和13:17日程示例，第二次用于补查；实际时间也应在启用前确认。GitHub 定时执行可能延迟或漏跑，不能当作保证准点的服务；见 [GitHub 定时运行说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。
